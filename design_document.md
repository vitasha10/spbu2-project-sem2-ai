# Design document: прогноз отмены бронирования отеля

Курс: Технологии ИИ, СПбГУ, весна 2026.
Авторы: Сухоплечев Виталий, Столярова Полина.

## Goal and Metrics

Задача - бинарная классификация: для каждой новой брони предсказать, будет ли она отменена до заезда. Целевая переменная `is_canceled` (0 - не отменили, 1 - отменили).

Зачем это бизнесу. Отели теряют деньги на отменах: если номер освобождается слишком поздно, его не получится продать заново. Если мы знаем заранее, что бронь с высокой вероятностью будет отменена, можно:
- запросить депозит или предоплату только с рискованных броней,
- держать overbooking-буфер,
- прицельно работать с клиентом (звонок, напоминание, подтверждение).

Метрики:
- основная: ROC-AUC. Классы не сильно разбалансированы (после очистки отмен около 27%), но нам важно именно ранжирование броней по риску, а не конкретное решение при threshold=0.5. ROC-AUC инвариантна к порогу и удобна для сравнения моделей.
- дополнительные: F1 по классу отмен и recall по классу отмен. Почему recall: пропущенная отмена (FN) стоит дороже ложной тревоги (FP). Если мы не предупредили, что бронь отменят, номер простоял пустым. Если мы перестраховались и попросили депозит у "нормального" клиента - в худшем случае клиент немного напрягся, но деньги не потеряны.

## Data

Источник: Hotel Booking Demand (Antonio, Almeida, Nunes, 2019, *Data in Brief* 22, 41-49). Две гостиницы в Португалии (City Hotel и Resort Hotel), данные за 2015-2017 годы, 119 390 строк, 32 колонки.

После чистки (дубли, строки с нулевыми гостями, выбросы adr, кандидаты на утечку) остаётся 86 970 строк, доля отмен 27%.

Ключевые признаки:
- `lead_time` - дней между бронированием и заездом. Самый сильный предиктор: отменяющие бронируют сильно заранее.
- `deposit_type` - тип депозита. Парадоксально, `Non Refund` почти всегда отменяют (особенность датасета, это описано и в оригинальной статье).
- `market_segment` - канал, через который пришла бронь. Online TA и Groups отменяют чаще всего.
- `previous_cancellations` - сколько раз клиент уже отменял. Прямой сигнал.
- `adr` - средняя суточная цена.
- `total_of_special_requests`, `required_car_parking_spaces` - вовлечённость клиента. Больше вовлечённости - меньше отмен.
- `country` - страна клиента. PRT (Португалия) отменяет заметно чаще остальных.

Колонки `reservation_status` и `reservation_status_date` удалены: это прямое описание того, отменили бронь или нет, использование их как фич = утечка.

Ограничения:
1. Только 2 отеля, одна страна размещения - обобщаемость на другие гостиничные сети под вопросом.
2. Период 2015-2017 - пост-ковидные паттерны бронирования могут отличаться.
3. Нет информации о цене конкурентов и внешних событиях (праздники, отмены рейсов) - модель опирается только на сам факт брони.

## Validation draft

Split: `train_test_split(test_size=0.2, random_state=42, stratify=y)`. Стратифицируем, потому что хотим равную долю классов в train и test.

Валидация на train: 5-fold StratifiedKFold (`shuffle=True, random_state=42`), `cross_validate` со scoring по ROC-AUC, F1, recall.

Почему random split, а не time-based. По-хорошему для брони надо было бы валидировать по времени (обучение на 2015-2016, тест на 2017) - это ближе к проду. Мы выбрали random stratified по двум причинам:
- баланс классов ощутимо меняется от года к году, при time-split одна метрика начинает "врать".
- в оригинальной статье Antonio et al. тоже делали random split.
При деплое это будет отдельным пунктом (см. раздел Deploy).

## Approach

Feature engineering (`src/features.py`):
- `total_nights`, `total_guests` - агрегаты; как правило работают лучше отдельных `stays_in_weekend_nights`, `adults` и т.п. в линейных моделях.
- `has_children`, `is_family` - семейные брони ведут себя иначе (реже отменяют).
- `room_changed = (reserved_room_type != assigned_room_type)` - эта группа почти никогда не отменяется (клиент либо уже заехал, либо вот-вот).
- `arrival_month_num`, `arrival_weekday`, `season` - сезонность.
- `adr_per_person` - нормируем цену на число гостей.
- `has_company` - бинарный флаг вместо почти пустой колонки `company` (94% NaN).

Кодирование категориальных:
- низкокардинальные (`hotel`, `meal`, `market_segment`, ...): OneHot для линейных моделей, OrdinalEncoder для деревьев и бустинга.
- высокая кардинальность (`country`, ~175 значений): TargetEncoder из `category_encoders` со сглаживанием 10. При K-fold CV encoding считается на train-folds отдельно для каждого split, что спасает от утечки.

Бейзлайн: DummyClassifier (most_frequent) даёт ROC-AUC = 0.5. Логистическая регрессия на OHE + scaled numerics + target encoding для country, с GridSearchCV по `C`.

Основные модели: kNN, Decision Tree, Random Forest, HistGradientBoostingClassifier.

## Training

Гиперпараметры (подбирали на 5-fold CV или фиксировали разумные значения):
- LogReg: `C=1` (из grid [0.01, 0.1, 1, 10]), `max_iter=2000`, solver lbfgs.
- kNN: `n_neighbors=30` (из [5, 15, 30]), на сабсэмпле 20k train строк (полный train слишком медленный при 100+ фичах).
- DecisionTree: `max_depth=10` (5, 10, None - без ограничения переобучается).
- RandomForest: `n_estimators=300`, `max_features='sqrt'` (по умолчанию), `min_samples_leaf=1`, `n_jobs=-1`.
- HistGradientBoosting: `max_iter=300`, `learning_rate=0.05`, `max_depth=8`.

Сводная таблица (ROC-AUC по 5-fold CV на train, для kNN - по сокращённой схеме):

| model          | ROC-AUC mean | ROC-AUC std | F1 (cancel) | recall (cancel) |
|----------------|--------------|-------------|-------------|-----------------|
| LogReg         | ~0.84        | 0.003       | 0.63        | 0.55            |
| kNN (sub)      | ~0.85        | -           | -           | -               |
| DecTree (d=10) | ~0.88        | 0.004       | -           | -               |
| RandomForest   | ~0.91        | 0.002       | 0.76        | 0.66            |
| HistGB         | ~0.92        | 0.002       | 0.77        | 0.67            |

Error analysis. Основные источники ошибок:
- FN (пропущенные отмены): короткий lead_time, нет предыдущих отмен, нет депозита, стандартный канал. По фичам такая бронь выглядит как обычная - модель не угадывает, потому что и не может угадать без дополнительных сигналов.
- FP (ложные тревоги): средний lead_time (1-3 месяца), рисковый канал (Online TA, Groups), без спец-запросов. Модель видит риск, а клиент всё-таки приезжает.

Сдвиг порога: при threshold=0.5 recall по отменам около 0.72 на тесте. Если порог сдвинуть вниз (например 0.35), recall растёт до 0.82 ценой падения precision. Конкретный порог выбирается бизнесом под свою цену FN и FP.

## Validation

ROC-AUC на 5-fold CV стабилен: std около 0.002-0.005 у всех моделей. На отложенном тесте HistGradientBoosting показывает ROC-AUC около 0.917 - совпадает с CV в пределах одного std, переобучения на test нет.

Калибровка вероятностей. По reliability plot видно:
- LogReg калиброван хорошо (почти на диагонали).
- RandomForest заметно задирает уверенность: предсказанные 0.9 соответствуют примерно 0.7 фактических отмен.
- HistGB ближе к диагонали, но всё равно слегка overconfident на хвостах.

Калибровка через `CalibratedClassifierCV(method='sigmoid')` выпрямляет reliability diagram. В продовой постановке это полезно, если конечный потребитель использует вероятность как число (например пороги "depos > 0.7, напомнить > 0.4"), а не только порядок.

## Model selection

Финальная модель: HistGradientBoostingClassifier с OrdinalEncoder для категорий. Выбран по:
- лучший ROC-AUC на CV и test (~0.92).
- самая низкая std по fold'ам среди сравниваемых.
- быстрее чем Random Forest c сопоставимым качеством.
- улавливает нелинейные взаимодействия (lead_time x deposit_type, market_segment x country), к которым LogReg не способен.

Риски и ограничения:
1. Перенос на другие отели. Обучались на 2 гостиницах в Португалии. На City Hotel в северной Европе распределение каналов и поведение клиентов может быть другим.
2. Сдвиг во времени (concept drift). Данные 2015-2017, поведение клиентов после 2020 года изменилось (отмены стали частью нормы из-за гибких условий).
3. Target encoding. Мы считаем encoding для country на out-of-fold, но на этапе инференса для новой страны (которой не было в train) encoding = глобальное среднее. Если в прод приходит новый рынок - качество на нём непредсказуемо.

## Deploy

Прототип: Streamlit-дашборд `app/app.py`. Форма с основными полями (отель, lead_time, deposit_type, market_segment, adr, special_requests, previous_cancellations и т.д.) -> вероятность отмены + цветовая подсказка.

Прод-версия (гипотетическая, для защиты):
- REST API на FastAPI с одним эндпоинтом `/predict`, принимающим параметры брони.
- Модель в виде `final_model.pkl`, грузится в память при старте сервиса.
- Онлайн-инференс при создании брони (latency не критична, < 50ms на запрос - pipeline с OrdinalEncoder + HGB быстрый).
- Плюс батчевый пересчёт раз в сутки по текущему пулу активных броней (lead_time уменьшается по мере приближения даты заезда, риск переоценивается).
- Мониторинг:
  - drift по распределению фич (`lead_time`, `market_segment`) с алертом если KS-тест > порога,
  - метрика по последним N броням, по которым уже есть факт отмены,
  - трекинг доли брони у которых `country` не было в train.
- Переобучение: раз в квартал на скользящем окне 2 года. При резком просадке метрик - досрочный цикл.
- Versioning: `final_model.pkl` + manifest с версией, хешем train-split, метриками на hold-out. Для rollback.

Интерфейс для рисёрчеров/аналитиков - те же самые ноутбуки из репозитория.
