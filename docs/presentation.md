## 1. Задача (~1 мин)

- Бинарная классификация: по параметрам брони предсказать, отменят ли её до заезда.
- Таргет: `is_canceled` (0 - доехал, 1 - отменили).
- Зачем: отель теряет деньги на отменах. Зная заранее риск, можно требовать депозит, держать overbooking-буфер или прозвонить клиента.
- Метрики: основная ROC-AUC, дополнительно F1 и recall по классу "отмена". Recall важнее precision: пропустить отмену дороже, чем напрасно перестраховаться.

## 2. Данные (~1.5 мин)

- Hotel Booking Demand, Antonio et al. 2019, *Data in Brief* 22.
- 119 390 строк, 32 колонки, 2 отеля в Португалии (City Hotel + Resort Hotel), 2015-2017.
- Доля отмен 37% - класс не сильно разбалансирован.
- 32 признака: lead_time, тип депозита, канал продаж, market segment, страна, история по клиенту, цена ADR, тип номера запрошенный и фактический, кол-во спецзапросов, парковка и т.п.
- Проблемы: пропуски в `country`, `agent`, `company` (последняя пустая на 94%), отрицательные и аномальные `adr` (одна строка 5400), строки с 0 гостей, дубли (~30 тысяч).
- **Утечка таргета:** `reservation_status` и `reservation_status_date` - это прямое описание исхода брони. Использовать их как фичи нельзя, удаляем.

## 3. EDA - ключевые наблюдения (~1.5 мин)

Показываем 3-4 графика из `01_eda.ipynb`:
1. **Баланс таргета:** 63% / 37%. Не нужны специальные техники для дисбаланса.
2. **lead_time vs отмена:** boxplot. Средний lead_time у отменивших почти в 2 раза больше. Это **главный** сигнал.
3. **deposit_type:** счётчик отмен. В группе `Non Refund` отменяют практически всегда. Парадокс датасета - формально невозвратные брони помечены так но фактически почти все пропадают. Это сильно тащит модель вверх.
4. **country:** PRT (Португалия) отменяет чаще всех, что логично - отели португальские, локальные могут бронировать "на всякий случай".
5. **room_changed:** когда номер реально меняли при заезде - почти никогда не отменяют (клиент уже на ресепшене).

Что выкидываем после EDA: `reservation_status*` (утечка), 32 тысячи дублей, строки с нулевыми гостями, выбросы по `adr`.

## 4. Препроцессинг и фичи (~1 мин)

`src/data.py` чистит, `src/features.py` лепит признаки. Сделали:

- агрегаты: `total_nights`, `total_guests`,
- бинарки: `has_children`, `is_family`, `room_changed`, `has_company`,
- временные: `arrival_month_num`, `arrival_weekday`, `season`,
- нормированная цена: `adr_per_person`.

Кодирование категориальных:
- низкокардинальные (`hotel`, `meal`, `market_segment`, ...) - **OneHot** для линейных, **OrdinalEncoder** для деревьев и бустинга.
- `country` (~175 значений) - **Target encoding** с `category_encoders.TargetEncoder`, smoothing=10. Чтобы избежать утечки, кодирование считается out-of-fold внутри CV.

Train/test split: 80/20, stratified по таргету, random_state=42.

## 5. Модели и сравнение (~2 мин)

5-fold StratifiedKFold cross-validation на train. Сравнили:

| Модель | ROC-AUC CV | Комментарий |
|--------|------------|-------------|
| Dummy (most_freq) | 0.500 | отправная точка |
| LogReg + GridSearch по C | ~0.84 | бейзлайн, не ловит нелинейности |
| kNN, k=30, на сабсэмпле | ~0.85 | страдает от размерности |
| DecisionTree, max_depth=10 | ~0.88 | без ограничения переобучается |
| RandomForest n=300 | ~0.91 | стабильно, но перекалиброван |
| **HistGradientBoosting** | **~0.92** | **лучший AUC и низкий std** |

Почему HGB выигрывает:
- ловит нелинейные взаимодействия (lead_time x deposit_type, market_segment x country), к которым LR не способен.
- встроенная обработка категорий через OrdinalEncoder.
- быстрее RF при сопоставимом качестве.

## 6. Финальная модель + калибровка (~1.5 мин)

- ROC-AUC на отложенном тесте: **0.917**.
- F1 по классу "cancel" около 0.77, recall 0.67 при threshold=0.5.
- Калибровка: показываем reliability plot до и после `CalibratedClassifierCV(method='sigmoid')`. RF задирает уверенность сильно (0.9 -> реально 0.7), HGB ближе к диагонали, после калибровки совсем хорошо.
- Permutation importance: топ-5 признаков - `lead_time`, `country`, `deposit_type`, `total_of_special_requests`, `market_segment`.
- Error analysis: FN - короткий lead_time + нет маркеров риска, отличить от обычной брони невозможно без доп. данных.

Финальная модель сохранена в `models/final_model.pkl` через joblib.

Запускаем Streamlit (`streamlit run app/app.py`, открывается на http://localhost:8501).

Показать **три быстрых сценария** через кнопки сверху:

## 8. Деплой и риски (~1 мин)

Прод (гипотетически):
- FastAPI с одним endpoint /predict, модель из pickle грузится в память,
- онлайн-инференс при создании брони + батч раз в сутки (lead_time уменьшается, риск пересчитывается),
- мониторинг drift по распределению фич + доли стран не из train,
- переобучение раз в квартал.

Главные риски модели:
1. **Перенос на другие отели.** Обучались на 2 отелях Португалии. На отель в Германии или сетевой бренд может не перенестись.
2. **Сдвиг во времени.** Данные 2015-2017, после 2020 поведение клиентов поменялось (гибкие условия отмены стали нормой).
3. **Target encoding.** Для новой страны (не было в train) encoding = глобальное среднее, качество на ней непредсказуемо.

## Что у нас точно спросят на защите

- Почему ROC-AUC? Классы не сильно разбалансированы, нам важно ранжирование броней по риску, а не конкретный порог.
- Почему recall важнее? FN (пропустили отмену) дороже FP (ложная тревога).
- Почему target encoding для country, а не OHE? 175 значений, OHE = 175 шумных колонок, target encoding даёт одну осмысленную.
- Как избежали утечки в target encoding? `category_encoders.TargetEncoder` внутри пайплайна считает encoding out-of-fold при CV.
- Почему HGB лучше? Ловит нелинейные взаимодействия, низкий std по fold'ам, быстрее RF.
- Что такое калибровка? Соответствие предсказанной вероятности фактической доле положительных в этой группе. Важно если используем число а не только порядок.
- Почему не нейросети? Запрещены условиями курса. Плюс для табличных данных бустинг обычно не хуже NN.
